# `getMarginAccount`, `getAccountEquity` and `getOpenOrdersOnchain` pin viem's cached block number, so right after the caller's own order they read a block from before it
Severity: normal
Area: SDK

## Steps to reproduce
1. `npm install` from the repo root (pins `@somnia-chain/markets-sdk` 0.32.1; it installs viem 2.57.7). The scripts use the SDK's default Hideki RPC and print JSON to stdout.
2. Use a testnet key with STT for gas and about 50 USDso of perps margin (the saved runs started with 49.6861, 49.6561, 49.6171 or 49.6151 USDso unlocked; the orders are the SOL minimum size, 0.1). Put the key in `PROBE_PRIVATE_KEY`.
3. Order list: `PROBE_PRIVATE_KEY=0x… CYCLES=20 node repro/016-open-orders-onchain-pinned-behind-own-receipt.mjs`. Each cycle: `trader.placePerpOrder` for a resting bid 20% below the mark, then at once `client.getOpenOrdersOnchain([pool], owner)` together with a raw `eth_blockNumber` POSTed to the same RPC (no cache); then the same read with `{ blockNumber: receipt.blockNumber }` and the control `client.getOwnOpenOrdersOnchain(pool, owner)`; then `trader.cancelOrder` and the same reads. The order never fills (about 40 small transactions). `RAW_FIRST=1` sends the raw `eth_blockNumber` before the pinned read instead (run 4). Runs 1 and 2 are from the version without the receipt-block read and the raw head, run 3 from the version without the raw head.
4. Margin reads: `PROBE_PRIVATE_KEY=0x… CYCLES=10 node repro/016-margin-reads-pinned-behind-own-fill.mjs`. Each cycle: an IOC market buy of 0.1 SOL (fills at the touch; the SDK returns the mined receipt), then at once `client.getMarginAccount` and `client.getAccountEquity`; then the closing IOC sell and the same reads. Control: `client.getPerpPosition` (no pin: one `readContract` without `blockNumber`, `dist/perp/state.js` lines 252-265). Each cycle costs the touch spread (the 10 cycles of run 1 lowered the account from 49.6861 to 49.6561 USDso, the `funds` field of the two margin evidence files); every cycle closes its own position.
5. The share of affected reads changes from run to run (see Actual): compare each read's block with the receipt's block in the printed rows.

## Expected
The SDK's own code says a head read for a change that was just made must not be cached. `dist/accountView/positionsClient.js` lines 224-226: "Uncached: viem reuses a head for up to its cache time, 500 ms on Somnia, and a read pinned there misses the change that asked for it.", then `client.getBlockNumber({ cacheTime: 0 })`. `dist/perp/adl.js` lines 230-232 say the same ("viem keeps the head for half a block time by default, and a read that an event asked for must not describe a block from before that event") and also pass `{ cacheTime: 0 }`, as does `dist/createClient.js` line 830.
The reads in this report are documented as chain-head reads. `getMarginAccount` "samples the chain head once and pins every component read to that block" (`dist/perp/margin.d.ts` lines 52-54); `getAccountEquity` reads through `getMarginEquity`, "pinned to one block" (lines 57-60). `getOpenOrdersOnchain` (JSDoc, `dist/orders.d.ts` lines 653-665): "Use when you must list your own resting orders and cannot depend on the indexer ... This read answers from the chain itself"; its `blockNumber` option is "Read at this exact block instead of pinning the current head" (line 647). The how-tos `docs/how-to/detect-fills.md` line 61 ("Read your own writes at chain head") and `docs/how-to/handle-errors.md` lines 127-128 tell the caller to read their open orders at chain head to learn whether a write happened; they name `getOwnOpenOrdersOnchain`, and `getOpenOrdersOnchain` is its full-rows sibling in the same read-tier table (`docs/reference/read-tiers.md` line 227).

## Actual
Right after the SDK has returned the receipt of the caller's own order, these three reads often pin a block from before that order: the placed order is missing, the cancelled one is still listed, the account shows no position after a fill. The block is a cached one. The reads pin with `getBlockNumber()` without `cacheTime: 0`: `dist/perp/margin.js` line 33 (`getMarginAccount`), line 66 (`getMarginEquity`, called by `getAccountEquity` at `dist/accountEquity.js` line 29), `dist/orders.js` line 574 (`getOpenOrdersOnchain`). The SDK creates its viem client without a `cacheTime` (`dist/client.js` line 885; the bound copy keeps `raw.cacheTime`, line 909), so viem's default applies: `cacheTime = pollingInterval`, 500 ms for `hidekiTestnet` (`blockTime: 10`, `dist/chains/definitions/hidekiTestnet.js` line 45; viem 2.57.7 `_esm/clients/createClient.js` lines 9-12, `_esm/actions/public/getBlockNumber.js` line 30). A read made within 500 ms of the previous one reuses that block, even when the caller's own transaction has been mined since.

Cause, run 5 (`evidence/016-run5-raw-head-concurrent.json`, 20 place + cancel cycles):
- After `placePerpOrder`, the pinned `getOpenOrdersOnchain` read a block 5 or 6 blocks behind the receipt in 16 of 20 cycles and missed the placed order in all 16. A raw `eth_blockNumber` sent at the same moment was already at or past the receipt's block in 15 of those 16. In 15 of the 16 the pinned block was exactly the block of the previous pinned read (the one after the previous cycle's cancel).
- After `cancelOrder`, 3 of 20 pinned reads were behind, by 1 block; in 2 of them the raw head was also 1 block behind. So the node can trail by one block too, but not by the 5 or 6 blocks the cache gives.
- Run 4 (`evidence/016-run4-raw-head-first.json`) sent the raw `eth_blockNumber` before the pinned read, which delays the pinned read past the cache window: 0 of 40 pinned reads were behind.

Order list, runs 1 to 3 (`evidence/016-run1.json` to `016-run3.json`; 20 cycles each), same signature:
- After `placePerpOrder`, the pinned read was behind the receipt in 8, 20 and 14 of 20 cycles, and the placed order was missing from `getOpenOrdersOnchain` in all of those. In 6 of 8, 19 of 20 and 13 of 14 the pinned block was the block of the previous cycle's post-cancel read.
- After `cancelOrder`, the pinned read was behind in 13, 2 and 6 of 20 and listed the already-cancelled order in 12, 2 and 6 of 20. In run 1, 11 of the 13 reused the block of the read made just before the cancel.
- Control: `getOwnOpenOrdersOnchain` (no pin: it passes `blockNumber` only when given, `dist/orders.js` line 490) agreed with the receipt in 100 of 100 placements and 100 of 100 cancellations over runs 1 to 5.
- `getOpenOrdersOnchain` with `{ blockNumber: receipt.blockNumber }` (runs 3 to 5): showed the placed order in 60 of 60 and the cancelled order gone in 60 of 60, with no read error.

Margin reads (`evidence/016-margin-run1.json`, `evidence/016-margin-run2.json`; 10 open + close cycles each, 0.1 SOL IOC fills, 100,000,000 base units each way in all 40 orders). They use the same `getBlockNumber()` call on the same client; the raw-head comparison was run on the order-list read only.
- After the opening fill, `getMarginAccount` was read at a block behind the fill's receipt in 4 of 10 (run 1) and 10 of 10 (run 2) cycles, and showed no active perp pool (the pre-fill account) in 4 of 10 and 9 of 10. `getAccountEquity`'s `asOfBlock` was behind the receipt in 4 and 10 of 10 (the evidence records its block, not the equity value). The control `getPerpPosition` showed the 0.1 SOL position in 10 of 10 and 10 of 10.
- After the closing fill, `getMarginAccount` was behind the receipt in 8 and 3 of 10 and still listed the pool as active in 7 and 2 of 10; `getAccountEquity` was behind in 8 and 3 of 10. The control showed flat in 10 of 10 and 10 of 10.

Every `getMarginAccount` and `getOpenOrdersOnchain` read that was behind showed a state from before the caller's write. In 4 cycles a "behind" count is one higher than the matching "shows the old state" count (cycle index `i` in the evidence rows: margin run 1 `i` = 2 and run 2 `i` = 1 after the close, margin run 2 `i` = 9 after the open, order run 1 `i` = 14 after the cancel). There the pinned block was also below the receipt of the transaction before (the opening fill, the previous cycle's close, the placement), so the read showed the state before that one.

Why it matters: code that checks its margin or equity right after its own fill can read the account as it was before the trade, and code that rebuilds its quote list from `getOpenOrdersOnchain` can see a quote it just placed as missing (a bot that trusts the list may place it twice) or a cancelled one as still resting. `getMarginAccount(marginBank, account)` takes no block option (`dist/somniaMarketsClient.d.ts` line 3212), so the caller cannot pin it to their receipt; `getAccountEquity` (`blockNumber`, `dist/accountEquity.d.ts` line 23) and `getOpenOrdersOnchain` can be pinned. The same cached pin is in `getBookTopsOnchain` (`dist/orders.js` line 249) and `drainOpenOrdersOnchain` (line 719); this report did not test them.

## Suggested fix
Pin with `getBlockNumber({ cacheTime: 0 })` in `getMarginAccount`, `getMarginEquity` and `getOpenOrdersOnchain` (and `getBookTopsOnchain`, `drainOpenOrdersOnchain`), as `dist/perp/adl.js` line 232, `dist/accountView/positionsClient.js` line 226 and `dist/createClient.js` line 830 already do. That removes the 5 to 6 block lag. For the occasional 1-block lag of the node itself (run 5), add a `blockNumber` option to `getMarginAccount` like the one `getAccountEquity` and `getOpenOrdersOnchain` have, and say in their JSDoc that passing the receipt's block is the read-your-writes path.
